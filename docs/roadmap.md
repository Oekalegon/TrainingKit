# TrainingKit — MVP Roadmap

High-level overview of the planned milestones. For the detailed MVP 1 package design (types, targets, test plan), see [`design/trainingKit-design.md`](design/trainingKit-design.md). Todo IDs referenced below are tracked in the `MVP1`/`MVP2`/`MVP3`/`MVP4`/`MVP5`/`MVP6`/`MVP7`/`FIT` projects.

Note: the numbering here has drifted from the design doc's own §12 "Roadmap seams" table, which only anticipates three post-MVP-1 milestones (plan generator, LLM coach, calibration). As scope got split further, the todo projects ended up as: MVP 2 (manual structured/planned workouts), MVP 3 (calibration — see its own note below), MVP 4 (activity detail, an MVP 1 spillover), MVP 5 (the plan generator/wizard), MVP 6 (the LLM coach), MVP 7 (Athlete tab biometric history). Treat the todo project numbers below as authoritative over the design doc's numbering.

---

## MVP 1 — Core, Persistence and Device Adapters

**Status: shipped in 0.1.0; the backlog below continues on `develop`.**

The foundation: the pure `TrainingCore` model (activities, training load / TRIMP, structured workouts, planned activities, the daily fitness series engine, periodisation, plan guardrails), the `TrainingHealthKit`/`TrainingWorkoutKit`/`TrainingPersistence` adapters, and the first iOS app (`TrainingApp`) — week view, activity detail, athlete account screen.

See §1–§10 of the design doc for the full model. Remaining MVP 1 work (backlog) is mostly UI polish and secondary features on top of the now-working core: HR-zone naming/colors, an 80/20 polarized-training split, HR-over-time/histogram charts on activity detail, an overlapping-activities warning, delete-activity support, and a fitness-metrics explainer sheet.

## MVP 2 — Structured & Planned Workouts

**Status: shipped in 0.2.0.** Still open from it: the marathon pace workout (needs pace zones, MVP 8) and adding a completed activity by hand from a past calendar day (MVP 4).

Manual authoring and scheduling, no auto-generation yet. Key pieces, scoped in detail through a design session (2026-09-13):

- **Navigation**: a new tab hosts the workout library (and, later, MVP 5's plan builder). The calendar's `+` on a date is date-aware: today/future opens a sheet to add a Planned Workout or a Race; a past date adds a completed Activity manually (deferred to **MVP 4**).
- **`Race` model**: dated event with a `RaceImportance` (primary/secondary/tertiary); primary is typically the plan's end date, secondary/tertiary get lighter plan adjustments — but that behavior is MVP 5's job, MVP 2 only stores/displays it (with a calendar marker distinguishing primary from secondary/tertiary).
- **`Goal` model**: a *separate* type from `Race` — a non-event target (e.g. "sub-20 5km") with no date and no calendar presence. Modeled in MVP 2 (`Goal` with a `GoalTarget` of time over a distance, a volume per week/month/year, or free text; a synced `GoalStore`; `TrainingModel.goals`); its management UI is an MVP 5 todo.
- **Structured Workout creator** (create/edit/duplicate) plus a standard library of running workouts: recovery, easy, long, tempo, fast finish, long fast finish, fartlek, long fartlek, hill reps, short/long/mixed interval, plus a MaxHR field test and an LTHR field test (Friel 30-min protocol). The creator itself shipped as MVP2-140 (a synced `WorkoutTemplateStore` on the kit side; the editor is in the app). Shipped so far: recovery, easy, long and tempo runs, plus Base Full-out hill sprints and Short interval run in time and track versions (MVP2-105), and (MVP2-106) Fast Finish Run, Long run with fast finish, Cruise, Long and Mixed Interval Runs, Fartlek (Zone 4 and Zone 5), Long Fartlek, Hill Repetition Runs and Sarcomere Runs (hill repetitions run downhill, at RPE 8 so the descent stays controlled). Run Elite templates from the user's notes: Alternation Run, Muscular Endurance Repeats, Speed Endurance Repeats, Long run with endurance intervals, Long run with speed intervals and Glycogen Store Run (zones follow the user's mapping of the book's percentages of race speed; the notes' examples are the defaults). Fartlek is two templates because a template's zone is fixed. The marathon pace workout waits for pace zones (MVP8). Duration-based by default; long/track workouts can be distance-based (multiples of 400/200/100m). `SessionType` deliberately stays a small, generic set of broad categories rather than growing a case per library workout; a template's specifics (fartlek, fast finish, the interval variants) live in the template itself. `StructuredWorkout` gets a `purpose` field (`.general`/`.maxHRTest`/`.lthrTest`); completing a test workout shows a "we measured X — update your profile?" confirmation rather than writing silently. `AthleteProfile` tracks *how* MaxHR/LTHR was obtained (`.formula`/`.workout`/`.labTest`, ranked by reliability in that order), with a manual lab-test entry path. The first part has shipped as MVP2-56: `HeartRateZoneSettings.maxHeartRateSource` (`.formula`/`.workout`), and a raise-only, athlete-confirmed max HR update whenever an ordinary workout holds a heart rate above the current max. The test workouts have shipped as MVP2-153: `StructuredWorkout.purpose` (and `WorkoutTemplate.purpose`, carried on instantiate, persisted, absent in old data = `.general`, and kept in calendar files) and the two built-in templates. The max HR test is a 10-minute Zone 1 warmup and 5-minute Zone 2 ramp-in, three 3-minute efforts at RPE 9 with 1-minute Zone 1 recoveries, a 3-minute all-out effort (RPE 10) and a 5-minute cooldown. Friel's LTHR test is the same warmup and ramp-in, one 30-minute effort at RPE 9, and a 5-minute cooldown; the result is the average heart rate over the effort's last 20 minutes. Both aim at perceived exertion, not heart-rate zones, because the zones are what the tests set. Measuring the results shipped as MVP2-154: `FieldTestMeasurer` and `TrainingModel.fieldTestResult(forActivity:)` read the max HR (the held peak) or the LTHR (the average of the last 20 minutes of the effort) off the activity linked to the test's plan, and `applyFieldTestResult` records it, date-effective, after the athlete confirms. A test may lower the max; ordinary workouts still only raise it. The source is `MaxHeartRateSource.fieldTest(activityID:)`, and `HeartRateZoneSettings.lactateThresholdSource` tracks the LTHR (`.manual` or `.fieldTest`). `.labTest(measuredOn:)` shipped as a source for both (entered by the athlete from a lab result), and the sources are ranked by reliability (`reliabilityRank(asOf:)`, `isReplaceable(by:asOf:)`: formula < manual < workout < field test < lab test) so an automatic update never replaces a better one. A lab test ages: after 2 years (max HR) or 90 days (LTHR) it ranks below a new field test. `FieldTestResult.replacesMoreReliableSource` warns when a test would replace a fresh lab value. The app shows the prompt (MVP2-155) and records lab tests in the heart-rate settings (MVP2-158).
- **Create/Edit Planned Workout sheet**: runs the hypothetical addition through the existing `PlanEvaluator` guardrails and warns (never blocks) on risk — one source of truth shared with MVP 5's generator rather than a second warning system.
- **TRIMP-confidence estimation** for planned/no-HR activities: map each step's `IntensityTarget` through the athlete's HR zones to a synthetic HR profile, run the existing TRIMP calculator, and label the result "estimated" vs "measured" everywhere it's shown. Once a structured workout has ≥1 completed activity linked via reconciliation, refine its estimate using the **median** actual TRIMP from those linked activities (a workout-specific precursor to MVP 3's general calibration, which supersedes it). Shipped as `LinkedActivityRefinedEstimator` (wrapped around the base estimator by `TrainingModel` for the load series and calendar export): the estimate of a workout is the base estimate times the recency-weighted median (a run's weight halves for every 60 days it is older than the newest run; a run whose duration is far from the workout's, such as a session cut short, is skipped) of `actual / base estimate` over completed plans of the same library workout or template. Comparing estimates (not raw TRIMP) is what scales it to the template's parameters and to the zones its steps target; confidence rises with each reference (0.7 → 0.85 → 0.925, capped 0.95). A per-plan `expectedLoadOverride` still wins.
- **`PlanReconciler`**: links a completed `Activity` to a `PlannedActivity` (an activity started from a scheduled Watch workout, `scheduledPlanID`, is matched to exactly that plan first; otherwise same-day, same-sport-family, best fit on the plan's explicit duration/distance; a close runner-up is flagged ambiguous rather than silently resolved; only newly imported activities are auto-matched, and manual links are same-day only). Manual link/unlink lives on the Activity Detail sheet.
- **Timeline card states**: *completed* (solid, leading vertical bar colored by type/effort), *planned-future* (same bar, hatched pattern, same hue, less saturated), *missed* — a planned workout whose date has passed with no linked activity (whole card hatched, secondary-color text throughout), and *merged* (solid like completed, showing both planned and actual duration/distance). A missed workout's estimated TRIMP is excluded from CTL/ATL/TSB, monotony/strain, and aggregate distance/duration stats — those reflect what actually happened; future planned workouts continue to feed the projected series as already designed.
- **Venue** (MVP2-151): `Sport` stays broad and a separate optional `Venue` (`.indoor(.treadmill/.track)`, `.outdoor(.track/.road/.trail/.offtrail)`) says where, carried by activities, workouts, templates, calendar exports and the athlete (`mainVenue`, the usual venue for `mainSport`). The venue is set on the WorkoutKit `CustomWorkout.location`, so starting a planned run on the Watch no longer asks "Indoor or Outdoor?". A template can leave the venue open, restrict it to outdoor, or fix it (the track intervals are an outdoor track); HealthKit's indoor-workout flag fills it on import. The athlete can change a performed activity's sport and venue (`TrainingModel.setSport`, flagged `isSportEdited` so re-imports and join rebuilds keep it; `refreshPaceHistory` follows). Unless edited, an activity linked to a plan takes the plan's sport and venue (else the athlete's usual venue, else the recorded one) on auto-match, manual link, re-import and join rebuild; the reconciler still matches indoor only with indoor and outdoor with outdoor. The plan editor's venue picker, the activity-detail picker and the default sport/venue setting are in the app.
- **Onboarding** (MVP2-147, shipped in the app): HealthKit + CloudKit permissions only (no profile setup). A first-run introduction explains both and can be left at any step, so it doesn't block the app. A dismissible banner covers "Health never connected" (once plans exist) and "iCloud isn't available" (the data stays on the device). HealthKit never says whether read access was granted or later turned off, so a revocation isn't detected: the Apple Health row says where to turn access back on. Initial-sync progress isn't shown.

This is the foundation the MVP 5 plan generator builds on: everything it produces is the same `PlannedActivity`/`StructuredWorkout` data a user can already create by hand here.

## MVP 5 — Plan Assistant

**Status: not started.**

The deterministic plan generator: `PlanPreferences` (training days, per-day sport/session-type, starting volume, weekly ramp), a Create Plan wizard sheet (training days, primary race/target, preferred long-run/interval days, recovery-week cadence, max TRIMP ramp), `PlanGenerator` that lays out cycles via `CycleLayoutBuilder` (already built in MVP 1) and fills them with library workouts, iterated against `PlanEvaluator`'s guardrails via a fixed set of heuristic adjustments — no LLM involved yet. Also covers a set of standard plans by target distance.

Groundwork laid for paradigms (MVP5-102/103): `CyclePhase` is a named, paradigm-defined value rather than a fixed enum, and each micro carries a separate `MicroLoadRole` (build/recovery/taper/race) that rules read instead of the phase (MVP5-113). Stored cycles written with the old enum still decode.

Training paradigms (MVP5-102): `TrainingParadigm` (named phases in order, `PlanGuardrails.Overrides`, the settings of three paradigm rules) with `IntensityMix` targets per phase, and `PlanSession` with a `SpeedLevel` next to `IntensityCategory` (hill sprints are low intensity but max speed). `PlanEvaluator` gains `intensityDistribution` (warning), `hardSessionSpacing` and `hardSessionsPerMicro` (risks), which run only when a paradigm is supplied. The built-in 80/20 and triphasic paradigms are MVP5-103.

Built-in paradigms (MVP5-103): `TrainingParadigm.polarized8020` and `.triphasic` (`builtIn` lists them), rules data only. Triphasic encodes its phases, the easy-only conditioning and base mixes, max-speed sprints as hard for placement, and 2-day spacing (3 days since MVP5-137); the structural/specific session profiles wait for MVP5-100, and layout (micro length, meso pattern, phase lengths) for the generator.

Polarized numbers (MVP5-136): reviewed and kept except per-phase `high` targets (base/taper 0.2, build 0.22, peak 0.25; medium 0, tolerance 0.05, 2 days between hard sessions, 2/3/4 hard sessions per 7/10/14-day micro, long runs spaced as hard); `PolarizedNumbersTests` pins them and their boundaries.

Longest-run rule (MVP5-116): `maxBuildProgressionFraction` and the `buildProgression` rule are gone; `PlanRule.longestRun` (a risk) flags a run more than `maxLongestRunIncreaseFraction` (10 %) longer than the longest planned run of the previous 28 days, by duration, any run type, from the `sessions` passed to the evaluator. `PlanGuardrails` now decodes tolerantly.

Volume curve (MVP5-117): `VolumeCurveBuilder` sets a `MicroVolumeTarget` per micro from a starting and a peak volume per 7 days (scaled by micro length): linear build ramp landing the peak in the last build micro, recovery at 0.6 of the preceding build, taper 0.7 to 0.5 of the peak, race 0.3; the adjust loop (MVP5-120) lowers micros where the guardrails ask.

Specific-phase intensity target (MVP5-114): `SpecificPhaseTarget` (`.pace(secondsPerKilometer:)`, `.heartRate(beatsPerMinute:)`, `.perceivedEffort(_:)`, `.predictedFromFitness` as a placeholder with no model yet) on the optional `Race.specificPhaseTarget`; `validate()` rejects non-finite, non-positive and out-of-range values, and a stored race without the field, or with an unknown or invalid target, decodes to `nil`. Only `StepTargetResolver` reads it so far (MVP5-122).

Day assignment (MVP5-119): `DayAssigner` places a micro's long runs, hard sessions and easy runs on its days and day parts from the availability, run types per weekday, `longRunPossible` and the paradigm's spacing and hard limit, and returns what it could not place as `DroppedSession`s with a reason; the athlete states the number of hard and long sessions, the generator (MVP5-145) reports the drops.

Ultra target (MVP5-138): `Race.distanceMeters` is required (`Race.isUltra`: longer than a marathon; a race without a distance no longer decodes, the store skips it); `TrainingParadigm.maxLongRunMeters` and `maxBackToBackLongRunPairsPerMicro` (both off by default) and `TrainingParadigm.resolved(for:)`; for an ultra target long runs are not spaced like hard sessions, and `DayAssigner` limits back-to-back long-run pairs per micro. `PlanPreferences.maxLongRunMeters` is the athlete's own ceiling and wins over the paradigm's. Defaults: a 35 km long-run ceiling, and 1, 1 and 2 pairs per 7-, 10- and 14-day micro in both built-ins.

Long-run flag (MVP5-139): `PlanSession.isLongRun` comes from the workout's own tag: `StructuredWorkout.sessionType` / `WorkoutTemplate.sessionType` (optional `SessionType`, nil = untagged = never long; decodes tolerantly; kept in the calendar file), `StructuredWorkout.isLongRun` is `sessionType == .long`, and `PlannedIntensityClassifier.session(on:for:athlete:)` reads it. The generator (MVP5-118/120) picks a `.long`-tagged workout for each `RunType.long` assignment of `DayAssigner`; the built-in templates are tagged since MVP5-118; the app's tag editor is still to do.

Template fit (MVP5-118): `WorkoutTemplate.analysis(athlete:)` gives a `TemplateAnalysis` (shortest/longest hard work step, work count, work time and duration over the parameter ranges); `SessionProfile` (session type, optional work-length and work-count ranges, optional race-target fraction) is held per phase by `TrainingParadigm.sessionProfiles` (empty for polarized; triphasic has the decided ones since MVP5-147); `TemplateFitter.fit` filters (running, not archived, tagged, ranges overlap), picks the closest fit by relative duration error, rotates off the previous micro's template within 10 points, and returns `.missingTemplate` when nothing passes; `SessionProfile.progressedWorkLength` steps the work length across a phase. The built-in templates are now tagged with a `SessionType` (the two field tests are not). The generator (MVP5-145) uses it; `StepTargetResolver` (MVP5-122, below) resolves step targets from the race-target fraction.

Step targets (MVP5-122): `StepTargetResolver.resolve(_:on:athlete:raceTarget:raceTargetFraction:)` is a pure function that writes concrete targets into a workout's steps and returns them with the steps it could not resolve (`StepTargetResolution`, `UnresolvedStep`, `UnresolvedReason`). A `.heartRateZone(n)` target becomes `.heartRateRange` (the date-effective bpm bounds) and the new `WorkoutStep.companionTarget` gets the zone's pace range (threshold pace times the zone multiplier, bounds halfway to the neighbouring zones); on a work step with a phase `raceTargetFraction` and a `.pace` race target the companion is instead `race pace / fraction` (a fraction of speed, 1.05 is faster) ±2 %, when it falls in the zone, else the step is reported as `paceOutsideZone` (the template does not suit the phase). A work step with no target takes that pace as its target. Explicit pace, power, heart-rate range and RPE targets are kept. No race target, a race target that is not a pace, no zones or an unavailable zone are reported, never guessed. The caller stores the resolved workout; the calendar file keeps `companionTarget` per step (optional `companionTarget`). The generator (MVP5-145) calls it for every run; reporting `unresolved` is still to do (the proposal has no compromise case for it); `TemplateFitter` does not yet reject templates whose zone cannot hold the phase pace.

Adjust loop and plan proposal (MVP5-120): `PlanAdjuster.propose(using:today:)` builds a plan through an injected `PlanCandidateProvider` (the generator's seam; `PlanLevers` in, `PlanCandidate` with cycles, workouts, sessions, projected series and compromises out), evaluates it with `PlanEvaluator`, and while a risk remains tries one `PlanAdjustment` (lower micro volume, down-week, ease or drop a session; gentlest first, kept only if the risks lessen or move closer to their thresholds, never the same levers twice, `maxIterations` 8). It returns a `PlanProposal`: all findings with `risks` and `warnings` separate (warnings never block and are not acted on), `PlanCompromise`s (lead time, unplaced sessions, missing templates, overridden preferences, kept adjustments), the iteration history and why it stopped; `draftPlan(named:)` and `stamped(with:)` make it a draft `TrainingPlan`. Steps `StepTargetResolver` could not resolve (MVP5-122) are not a `PlanCompromise`: the generator (MVP5-145) behind the provider calls the resolver but does not report them yet.

Plan preview and commit (MVP5-121, package side): `PlanCandidate.workouts` (the workouts the planned workouts refer to), `TrainingModel.preview(_:asOf:)` returning a `PlanPreview` (layout, workouts, projected form, compromises, risks, warnings, and the active plan's upcoming uncompleted workouts that activation would replace) and `TrainingModel.commit(_:named:activate:acceptingRisks:asOf:)` (workouts to the library, draft plan with stamped cycles and workouts in one write, optional activation; risks block activation unless accepted, never a draft; `PlanProposalError`). The screens, in TrainingApp, are still to do; the generator behind the provider is MVP5-145.

Plan generator (MVP5-145): `PlanGenerator.generate(_:)` (a `PlanRequest` in, a `PlanProposal` out, async and cancellable, deterministic apart from ids) is the `PlanCandidateProvider` behind `PlanAdjuster`. It composes the lead-time compromiser, key-race layout, cycle layout, volume curve (peak capped by `maxWeeklyVolume`), day assigner, template fitter (rotation, progression), step-target resolver, the intensity classifier and the load series, and adds no rules or numbers. Equal split of a micro's duration over its runs, a plain session profile where the paradigm has none, errors for what leaves no plan (`PlanGeneratorError`) and compromises for what does; unresolved steps, skipped key races, a later start and the long-run ceiling are not reported yet. Data flow in the design doc, "Plan generator". Still to do: the app wizard (MVP5-121, TrainingApp) and re-plan from today (MVP5-123).

Triphasic plan quality, part 1 (race day and race load): `DayAssigner.assign(... raceDays:)` leaves a race day empty and the generator passes the target race and the other races, so the race day carries no easy run; `DailyLoadSeries.days(... races:)` adds each race's load on or after today (`Race.expectedLoadOverride`, else a `TRIMPPlanEstimator` estimate from the distance and `specificPhaseTarget`; every priority counts) and `TrainingModel` and the generator pass their races, so a 100 km race no longer leaves the TSB in detraining; the generator accepts distance volumes (converted at the zone-2 pace) and still rejects TRIMP. Evaluations change as follows: the last micro has one run fewer, the race-day series has the race's load, and plans for a race with later days see the race's fatigue. Parts 2 to 4 (triphasic session profiles, spacing and hard-session defaults, TSB-zone sizing, strain on a ramp) follow. App follow-ups: ask for the starting distance and the peak distance in the wizard, offer `Race.expectedLoadOverride`.

Triphasic plan quality, part 2 (target workouts and spacing): `TrainingParadigm.triphasic` gets `minDaysBetweenHardSessions` 2 (was 3) and `sessionProfiles` for what the design doc decides (base hill sprints; structural fast and endurance quality with the book's work lengths and drifting race-target fractions; specific and taper asking for race-pace work, from a template whose zone holds the pace, checked since MVP5-150); `SessionProfile.endRaceTargetFraction` and `progressedRaceTargetFraction(microIndex:of:)` move a fraction across a phase; a micro's hard runs take the phase's hard profiles in turn, starting at the micro's position in its phase (so a single hard run alternates between them); `PlanPreferences.minDaysBetweenHardSessions` overrides the paradigm's spacing for the assignment and the evaluation; `PlanRequest.hardSessionsPerMicro` defaults to 2, 3 and 4 for 7, 10 and 14-day micros (was 1). `MesocycleTemplate.twoToOne` already exists for a recovery micro every third micro. Evaluations change: a triphasic plan has hill sprints in base and intervals with the book's work lengths in structural, spacing of 2 is no longer flagged, and with Tuesday and Thursday as the only hard days a 10-day micro that holds fewer than three of them reports the third session as `unplacedSession`. Open: the alternation run's own spacing (Q5 c), the specific work lengths (Q3), and `TemplateFitter` rejecting templates whose zone cannot hold the phase's race-target pace (today the step keeps its zone target and is not reported, so race-pace work may be planned with a Z2 or Z3 template). App follow-ups: ask for the number of hard sessions per micro and phase, the recovery cadence (pass `.threeToOne` or `.twoToOne`) and the spacing.

Triphasic plan quality, part 3 (TSB zones): `PlanGenerator` sizes each micro to the middle of its TSB zone at its end (`TSBZone.midpoint(guardrails:)`: training −20 for a build micro, recovery −2.5 for a recovery micro, race 15 on race day for a taper micro), with the volume curve as a ceiling (recovery and taper micros are bounded by the ramp, not by the old fractions) and the curve's own volume while the aimed day is warming up. The athlete's own peak is never exceeded, so a micro already fresher than its aim at the ceiling stays there: with realistic volumes build micros often end in the recovery zone, not at −20. A micro no volume brings to its aim gets the lightest volume tried; the lever `volumeScales` multiplies the sized volume. Evaluations change: build micros end in the training zone and recovery micros in the recovery zone, race day is in the race zone (the taper is sized, so it is not fixed at 0.7 to 0.5 and 0.3 of the peak), the TSB band findings of the first plan fall away, and generating takes about 3 times as long (a few bisection steps per micro). App follow-up: tell the athlete when a micro stays above its aim because the entered volume is too low for the zone.

Triphasic plan quality, part 4 (strain on a ramp): `PlanEvaluator` skips the strain rule for a series with fewer than 14 days of real (not projected) strain, so a plan that ramps up from no history no longer gets a strain risk on nearly every day (30 in the first real plan); with history the rule is unchanged (a spike above the 95th percentile of the trailing 84 days). Decided with the user on 2026-10-27.

Recovery days per template (MVP5-147): `WorkoutTemplate.recoveryDays` (`RecoveryDays(before:after:)`) is the days a workout wants free of demanding workouts around it, with defaults by session type (intense 0 before and the paradigm's spacing after, easy and recovery none) and 1 and 3 for the alternation run; the days are minimums to aim for. `PlanGenerator` refits a run without a template that wants more than its neighbours leave, keeps it with `PlanCompromise.recoveryDaysShort` when nothing else fits, and `DayAssigner(recoveryAfter:)` keeps a hard session clear of a workout in the micro before where it can. The calendar file carries the days; `PlanEvaluator` does not check them yet. Open: special blocks that may break the rule are not modelled. App follow-ups: handle the new `PlanCompromise.recoveryDaysShort` case in exhaustive switches, and let the template editor set the days.

Faster sizing and a report (MVP5-151): the TSB-zone sizing spent about 90 % of its time in `TemplateFitter`, not in the series. The fitter solves a duration that is linear in a parameter in closed form (checked at the answer, bisection otherwise), `PlanGenerator` prepares the templates once and fits equal runs of a micro once; the plan suites run about 1.7 times faster with the same plans. A micro that ends in another TSB zone than its role aims at is now `PlanCompromise.sizingMissedZone(microStart:aimed:reached:)` (not for a micro the adjust loop lowered). Not done: seeding each probe's series with the committed CTL/ATL, which would save little. App follow-up: handle the new case in exhaustive switches and show it in the plan preview, grouped by `(aimed, reached)`: with volumes near the athlete's history nearly every build micro misses the training zone, and the advice (a higher starting or peak volume) is the same.

Race load in the statistics and the sandbox series (MVP5-149): `SeriesEngine.metrics` has a `races` argument (a protocol change for every conformer; `DefaultSeriesEngine` no longer takes races at init) and `PlanSandbox.simulate` passes its races. `StatisticsCalculator.weeklyStats`, `periodStats` and `periodStatsSplit` take `races:` (default none) and count a race from today on like a planned activity: its distance, duration and time in zone from the one-step race workout, its load as `DailyLoadSeries` adds it, and one activity. A `PlanSandbox` that already had races now also puts their load in the series it evaluates, so its findings after a race change (a long race can raise a TSB band finding). App follow-ups: pass the athlete's races to the statistics calls, update any `SeriesEngine` conformer, and expect post-race findings from the sandbox tools.

Race-pace work in the right zone (MVP5-150): a profile with a race-target fraction on a pace target only takes templates with a hard work step in a zone whose pace range holds the phase pace (race pace divided by the fraction), whatever that zone is: a zone 3 race pace gets zone 3 work. With no such template the best fit is kept and the plan reports `PlanCompromise.unresolvedStep(microStart:template:reason:)` for a hard step that could not be given its target (once per template and reason in a micro), among them `noRaceTarget` for a race without a pace target. Easy steps of a template are not reported. App follow-ups: handle the new case in exhaustive switches and show it in the plan preview; asking for a goal pace avoids most reports. Open: the structural endurance quality profile (86 % to 94 % of race pace) has no built-in template whose hard zone holds that pace for a marathon pace in zone 3, so it is reported until a template or a decision on the fractions exists.

Short lead time (MVP5-115): `LeadTimeCompromiser.adjust(_:paradigm:leadTimeDays:microLengthDays:preferences:)` fits a paradigm's full `MacroTemplate` into a shorter lead time (whole micros): conditioning is dropped, then structural, then the paradigm's `shortenablePhase` (specific for triphasic, peak for polarized) is shortened to a minimum (1 micro by default), then the oldest blocks are trimmed; the taper is never cut, and a lead time below taper plus the minimum throws `LeadTimeError.leadTimeTooShort`. It returns the macro and a `LeadTimeCompromise` per change (typed action, `leadTimeTooShort` reason, `overriddenPreference`). New `PlanPreferences.includeConditioning` (default false) and `TrainingParadigm.shortenablePhase`. The generator (MVP5-145) passes the compromises on, the plan preview (MVP5-121, TrainingApp) lists them; the proposal lists them as `PlanCompromise.leadTime` (MVP5-120), not as findings.

Triphasic written down (MVP5-100): `docs/design/triphasic-design.md` sets out, phase by phase, what the user's Run Elite skills say (session types, work lengths where given, race-speed fractions, mixes, hard sessions per micro and spacing, phase lengths and how they flex with the lead time, micro length, the taper) and compares each number with `TrainingParadigm.triphasic`, `SessionProfile`, `StepTargetResolver` and `LeadTimeCompromiser` (match, differs, not modelled), with a table of open questions. The paradigm and its numbers are unchanged; the same change adds the Run Elite workout templates listed above. MVP5-137 dials the triphasic numbers from it and MVP5-138 covers ultra.

Triphasic numbers (MVP5-137): mixes for structural (`high` and `fast` 0.10, `medium`/`moderate` 0, ±0.10), specific and taper (`medium`, `high`, `moderate`, `fast` 0.25 ±0.25) and 3 days between hard sessions, set with the user on 2026-10-22 (changed to 2 on 2026-10-27, MVP5-147); base keeps 0 ±0.05 and no max-speed ceiling, no per-micro limit, hard unchanged. ## FIT — Garmin/COROS Import (TrainingFIT)

**Status: not started; scope actively being defined.**

A `TrainingFIT` target/second `ActivityImporting` implementation for Garmin/COROS data, sitting alongside `TrainingHealthKit` and `WorkoutKitBridge`. Already-filed scope:

- **FIT/TCX activity import and FIT workout export** (`FIT-1`, `FIT-2`) — the baseline: read a raw Garmin/COROS `.FIT`/`.TCX` file, export `StructuredWorkout`s as `.FIT` workouts.
- **Attach a raw `.FIT` file to backfill sparse-HR activities** (`FIT-3`) — for activities that already exist (e.g. from HealthKit) but are missing HR/GPS detail.

### Strava as a relay for Garmin data

Garmin auto-syncs completed activities to Strava, and Strava's Activity Streams API exposes `heartrate`, `latlng`, and `altitude` streams per activity. That's a second, complementary path into the same Garmin data — no direct Garmin API access needed — alongside the file-based FIT import above. Newly scoped:

- **Strava relay import** (`FIT-4`) — a Strava activity-source/provider adapter that pulls HR/GPS/elevation streams via `get_activity_streams`, keyed by activity ID from `list_activities`.
- **Per-activity import picker** (`FIT-5`) — in the activity detail view, let the user import/attach data for that one activity from either a local `.FIT` file or Strava.
- **Automatic background sync** (`FIT-6`) — periodically pull new Strava activities without a manual per-activity action, once the relay adapter exists.
- **Throttled historical backfill** (`FIT-7`) — Strava's rate limits (15-min and daily caps) make importing an athlete's full history in one shot risky. Investigate a gradual backfill — a bounded batch of older activities per sync cycle — rather than a bulk one-time pull.
- **Duplicate detection & merging across sources** (`FIT-8`) — an activity can now arrive from HealthKit, a `.FIT` file, and Strava. Detect when an incoming activity is the same session as one already stored (matching on time/duration/sport, extending MVP 1's existing `ActivityStore.upsert` dedupe-by-source work, `MVP1-26`/`MVP1-27`/`MVP1-28`) instead of creating a duplicate — but allow genuinely merging data from multiple sources into one activity record.
- **Field-level conflict resolution on import** (`FIT-9`) — when a new import targets an activity that already has data from another source (e.g. FIT-file HR arriving for an activity that already has Strava-derived HR), ask the user which fields to keep vs. replace rather than silently overwriting or silently skipping.

Open question carried over from the discussion: whether the throttled backfill (`FIT-7`) is feasible within Strava's rate limits for a typical athlete's multi-year history, and what a sensible default batch size/cadence looks like — needs investigation before `FIT-7` can be scoped into concrete steps.
